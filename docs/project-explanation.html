1. What Is This Project?

This is an automated testing project for the website saucedemo.com (a demo e-commerce site). Instead of a human manually clicking through the website to check if everything works, we wrote Java code that opens a browser, clicks buttons, fills forms, and checks results automatically.

In simple terms: We wrote a robot that tests a shopping website by logging in, browsing products, adding items to cart, checking out, and verifying everything works correctly. If something breaks, the robot tells us exactly what went wrong with a screenshot.

The project uses these core technologies:

TechnologyWhat It Does
Java 11The programming language we write our test code in
Selenium WebDriverControls the browser (opens pages, clicks buttons, reads text)
TestNGThe test framework that runs our tests and reports pass/fail
MavenManages all libraries and builds the project
Page Object ModelA design pattern that keeps our code organized and reusable

2. Why Maven?

Maven is a build tool. Think of it as a project manager for your code. Here's what it does:

  • Downloads libraries automatically — Instead of manually downloading Selenium JARs from the internet, we just list them in pom.xml and Maven fetches them
  • Compiles our code — Converts our Java files into runnable code
  • Runs tests — One command (mvn clean test) compiles everything and runs all tests
  • Generates reports — Works with Allure to create visual test reports
  • Keeps versions consistent — Every team member gets the exact same library versions
Without Maven: You'd manually download 20+ JAR files, set up classpaths, and hope everyone on the team has the same versions. Maven does all of this with one file (pom.xml).

6. Base Test Class

BaseTest.java

Every test class extends this. It handles the boring-but-essential browser setup and cleanup.

MethodWhen It RunsWhat It Does
setUp() Before every single test method 1. Reads which browser to use from config
2. Creates a new browser instance (Chrome, Firefox, or Edge)
3. Applies headless mode if configured
4. Maximizes the browser window
5. Opens the saucedemo.com URL
tearDown() After every single test method Closes the browser completely. This ensures each test starts fresh with a clean browser.
getDriver() Called by TestListener Returns the browser driver so the listener can take screenshots on failure.
Why a fresh browser per test? If tests share a browser, a failure in one test (like a broken login) could cause all following tests to fail too. Fresh browser = independent tests.

7. Page Objects (Where Locators Live)

We use the Page Object Model (POM) design pattern. Each page of the website gets its own Java class. That class stores:

  • Locators — How to find elements on that page (IDs, CSS selectors, class names)
  • Methods — Actions you can perform on that page (click a button, read text, fill a form)
Why POM? If a developer changes a button's ID on the website, we only fix it in ONE place (the page class), not in every test that clicks that button. Without POM, you'd be hunting through 45 test methods to find and fix every reference.

8. Utilities

ConfigReader.java

Reads values from config.properties. Uses a static block, so the file is loaded once when the class first loads.

MethodWhat It Does
get(key)Returns a string value (e.g., ConfigReader.get("browser") returns "chrome")
getInt(key)Returns an integer value (e.g., ConfigReader.getInt("explicitWait") returns 10)

WaitUtils.java

Wraps Selenium's WebDriverWait with easy-to-use methods. The timeout comes from config.properties (10 seconds).

MethodWhat It Does
waitForVisible(locator)Waits until the element is visible on the page, then returns it
waitForClickable(locator)Waits until the element can be clicked, then returns it
waitForInvisible(locator)Waits until the element disappears from the page
Why explicit waits instead of Thread.sleep? Thread.sleep(3000) always waits 3 seconds even if the element appears in 0.5 seconds. Explicit waits check every 500ms and move on as soon as the element is ready. This makes tests faster and more reliable.

ScreenshotUtil.java

Captures browser screenshots. Called automatically on test failure by the TestListener.

MethodWhat It Does
capture(driver, testName)Saves a PNG screenshot to screenshots/ folder with timestamp. Returns the file path for the Extent report.
captureAsBytes(driver)Returns screenshot as a byte array for Allure attachment.

9. Listeners (Reports & Retry)

TestListener.java

Implements TestNG's ITestListener interface. It automatically reacts to test events:

EventWhat the Listener Does
Suite startsCreates the Extent report file at reports/ExtentReport.html with title, theme, and system info
Test startsCreates a new entry in the Extent report for this test
Test passesLogs PASS status in the report
Test failsLogs FAIL status + error message, captures screenshot (saved to file for Extent, byte array for Allure), records the URL where the failure happened
Test skippedLogs SKIP status with reason
Suite finishesSaves and closes the Extent report file

RetryAnalyzer.java

If a test fails, this retries it up to retryCount times (default 1). This helps with flaky tests — tests that sometimes fail due to timing issues, not actual bugs.

RetryTransformer.java

Automatically applies the RetryAnalyzer to every @Test method. Without this, you'd have to manually add retryAnalyzer = RetryAnalyzer.class to each @Test annotation.

Test Groups

Tests are tagged with groups so you can run specific subsets:

  • smoke — Quick sanity checks (run these first to verify basics work)
  • regression — Full test suite (run these to verify nothing broke)

Run only smoke tests: mvn test -Dgroups=smoke

11. testng.xml

This XML file tells TestNG which tests to run and how:

  • Suite name: "SauceDemo Test Suite"
  • Parallel execution: Runs test groups in parallel using 3 threads (3 browsers open at once)
  • Listeners: Registers TestListener (for reports) and RetryTransformer (for auto-retry)
  • 8 test blocks: One for each test class, run in order: Setup, Login, Product Listing, Product Detail, Shopping Cart, Checkout, Navigation, End-to-End

12. Reports & Screenshots

Extent Reports

A standalone HTML file you open in a browser. Shows pass/fail counts, each test with its status, and embedded screenshots for failures. Generated automatically by TestListener.java.

Allure Reports

An interactive report that opens in a browser via mvn allure:serve. Shows tests organized by Epic/Feature/Severity, step-by-step execution logs (via @Step), failure screenshots, timeline view, and trends over multiple runs.

13. How It All Connects

Here's the flow when you run mvn clean test:

mvn clean test
→
Maven reads pom.xml
→
Downloads dependencies
→
Compiles Java code
→
Reads testng.xml
TestNG starts suite
→
TestListener initializes Extent report
→
For each test method:
BaseTest.setUp() opens browser
→
Test method runs using Page Objects
→
Assert checks results
→
Listener logs pass/fail + screenshot
→
BaseTest.tearDown() closes browser
Suite finishes
→
Extent report saved
→
Allure results saved
